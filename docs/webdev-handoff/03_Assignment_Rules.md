# GD/VE TeamFlow - Assignment Rules

Date: 2026-05-15  
Scope: Creative Requests only

## 1. Principle

The assignment engine exists to solve the main pain points:

- distribute work fairly
- match work to the right skill
- respect capacity
- avoid work piling on the same person
- keep assignment explainable

Quick Tasks do not use the assignment engine by default.

## 2. Assignment Trigger

Run assignment when:

- a complete Creative Request is submitted
- a `Need Brief` request becomes complete
- a queued request is manually rechecked
- member capacity or availability changes
- an admin/coordinator reruns assignment

## 3. Assignment Inputs

From request:

- asset type
- asset subtype
- platform
- size/format
- priority
- due date
- launch date
- brief completeness
- effort point
- needs split flag

From team member:

- skills
- availability
- capacity per day
- capacity override
- current assigned effort
- current WIP
- WIP limit
- active/inactive

## 4. Brief Completeness Check

Before assignment, backend must check required creative fields:

- title
- requester team
- campaign name
- asset type
- asset subtype
- platform
- size/format
- brief link
- due date
- launch date
- urgent reason if priority is urgent

If incomplete:

```text
status = Need Brief
assignment_result = need_brief
```

Do not calculate final assignment until brief is complete.

## 5. Effort Point Rule

One effort point roughly equals one production hour.

Requester cannot manually input effort point.

Effort point is generated by backend and capped at 8.

| Category | Stored Effort |
|---|---:|
| Simple banner / ad visual | 2 |
| Standard banner / complex social content | 4 |
| Esport graphic pack - minor | 3 |
| Esport graphic pack - complete set | 8 |
| Short-form content / TikTok / Reels | 4 |
| Standard video / YouTube vlog | 6 |
| High-retention short video | 7 |
| Promotional esport or highlight reel | 8 |
| Hybrid creative request | 8 and `needs_split = true` |

## 6. Capacity Model

Use effort per day for assignment.

Recommended calculation:

```text
working_days_until_due = count working days from today to due_date
available_window = effective_capacity_per_day * working_days_until_due
assigned_load = sum effort for open assigned creative work due on or before due_date
remaining_capacity = available_window - assigned_load
can_assign = effort_point <= remaining_capacity
```

Open assigned creative work includes:

- Assigned
- In Progress
- Review
- Blocked

Delivered and Cancelled do not count.

## 7. Availability Rules

### Available

Use normal capacity.

### Partial

Use capacity override.

If capacity override is missing:

```text
do not assign normal work
exclude from available capacity
show partial capacity warning
```

### On Leave

Capacity equals 0 and member cannot receive new assignment.

## 8. WIP Rule

WIP means currently active production, not every assigned task.

Count WIP when:

```text
status = In Progress
wip_counted = true
```

Do not assign if member current WIP is already at or above WIP limit.

## 9. Routing Rules

| Asset Type | Routing |
|---|---|
| `static-graphic` | Static graphic designers by skill, WIP, and capacity |
| `general-video` | General video capable member |
| `motion` | Motion capable member |
| `esport-video` | eSport video capable member first |
| `esport-video` fallback | Backup video member only if urgent and capacity allows |
| `hybrid` | Stay Queued and require split |

Example current team routing:

| Member | Skills |
|---|---|
| Pond | static graphic, general video, motion, esport video backup |
| Jo | static graphic |
| Tong | static graphic |
| Eye | static graphic |
| Vee | esport video |

## 10. Hybrid Rule

Hybrid work should not be automatically assigned as one task in MVP.

Reason:

- Static and video work may need different people.
- One owner would hide real workload.
- Capacity calculation becomes unreliable.

MVP behavior:

```text
asset_type = hybrid
effort_point = 8
needs_split = true
status = Queued
assignment_reason = "Queued: hybrid request must be split into separate static/video requests."
```

Manual split can be handled by creating separate Creative Requests.

## 11. Candidate Filtering

A member is eligible only if all are true:

1. Active member.
2. Has required skill.
3. Available or Partial with override.
4. Not on leave.
5. WIP below limit.
6. Remaining capacity can fit effort.
7. Routing rule allows assignment.

## 12. Tie-Breaker

If multiple members are eligible, choose in this order:

1. Highest remaining capacity before due date.
2. Lower current WIP.
3. Lower assigned effort.
4. Fewer overdue active items.
5. Stable member code order.

Stable order prevents random assignment.

## 13. Queue Reasons

If no eligible owner, keep request in `Queued`.

Recommended reasons:

- brief incomplete
- no matching skill
- all matching members at WIP limit
- all matching members over capacity
- member partial capacity unclear
- member on leave
- hybrid request requires split
- due date too close for available capacity

Queue reason must be human-readable.

## 14. Status Output

Assignment result can be:

### Assigned

```json
{
  "status": "Assigned",
  "final_owner_member_id": "member-id",
  "effort_point": 4,
  "assignment_reason": "Auto: static graphic assigned by skill, WIP, and remaining capacity."
}
```

### Queued

```json
{
  "status": "Queued",
  "final_owner_member_id": null,
  "effort_point": 4,
  "assignment_reason": "Queued: all static graphic designers are at capacity before due date."
}
```

### Need Brief

```json
{
  "status": "Need Brief",
  "final_owner_member_id": null,
  "assignment_reason": "Need Brief: brief link and size/format are required."
}
```

## 15. Review Round Rule

Only backend can increment `review_round`.

Increment when:

```text
Review -> In Progress
reason = requester requested changes
WIP check passes
```

Do not increment when:

- request is blocked
- request remains in Review because WIP is full
- owner edits delivery link
- requester approves delivery

## 16. Fairness Guardrails

The system should avoid repeatedly assigning to the same person when others are eligible.

Use:

- remaining capacity
- WIP
- assigned effort
- overdue count

Do not use random assignment.

## 17. Manual Override Policy

MVP recommendation:

- Do not allow requester to choose preferred owner.
- Do not allow normal users to manually assign creative requests.
- Allow "rerun assignment" only.

If manual override is needed later:

- restrict to coordinator/supervisor
- require override reason
- write audit event
- show override in assignment history
